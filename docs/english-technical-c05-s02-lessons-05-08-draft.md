# Lesson 5. Manufacturing Process Review and Improvement

**ID:** `en-c05-s02-l05` · **Level:** B2 · **Suggested duration:** 90 minutes

## Learning outcomes
Students can describe a manufacturing process at a high level, compare process records, identify an improvement opportunity without inventing a cause, discuss quality evidence and present a cautious recommendation.

## 1. Lead-in
Discuss:
1. What is the difference between a process description and a process evaluation?
2. Which records can help a team understand a manufacturing process?
3. Why should an improvement proposal be based on evidence?
4. Why is a small sample not enough to prove that a process has improved?

## 2. Key vocabulary

| Term | Russian | Example |
|---|---|---|
| process flow | схема процесса | The process flow shows the main stages. |
| work sequence | последовательность работ | The work sequence is described in the training sheet. |
| process parameter | параметр процесса | The sample record lists a fictional process parameter. |
| batch record | запись о партии | The batch record identifies the training batch. |
| traceability | прослеживаемость | Traceability connects a record with its source. |
| bottleneck | узкое место | The review identified a possible bottleneck. |
| variation | вариация, разброс | The sample shows variation between records. |
| baseline | исходный уровень | The baseline is needed for comparison. |
| improvement proposal | предложение по улучшению | The proposal requires review. |
| outcome | результат | The outcome should be measured. |
| constraint | ограничение | Time is one project constraint. |
| evidence | доказательства, данные | The recommendation must be supported by evidence. |

## 3. Reading: reviewing a process without jumping to conclusions

A process review examines how information, materials or tasks move through a defined sequence. A reviewer may compare process maps, work records, quality summaries and feedback from the people involved. The aim is to understand the process and identify questions that deserve further investigation.

A useful review separates four elements:

- **Description:** what the documented process says.
- **Observation:** what the available records show.
- **Interpretation:** what the observation may mean.
- **Proposal:** what could be reviewed or tested by the responsible team.

For example, a fictional classroom table may show that one training record contains more handover notes than another. This is an observation. It does not prove that one team works more efficiently. The records may cover different tasks or different time periods.

A responsible improvement proposal states its assumptions, evidence and limitations. It does not promise a result before a controlled evaluation has taken place.

### Fictional process-review table

| Training stage | Records reviewed | Note |
|---|---:|---|
| Material identification | 8 | 1 record needs a clearer source reference |
| Process documentation | 8 | 2 records use different terms |

## 5. Language focus: comparing evidence and making proposals

Comparisons:
- “Compared with the first sample…”
- “The second record contains fewer details.”
- “Both versions include…”
- “The main difference concerns…”

Cautious recommendations:
- “The team could consider…”
- “It may be useful to review…”
- “Further evidence would be needed before…”
- “The document owner should confirm…”

### Exercise A — choose the accurate statement
1. The sample contains three missing action-owner fields.
   a) “Three records in the sample do not identify an action owner.”
   b) “The entire production system has failed.”
2. The cause is unknown.
   a) “The cause is confirmed.”
   b) “The cause has not been established.”
3. A template may need review.
   a) “The team could review the template.”
   b) “The template must be replaced immediately.”

**Key:** 1a; 2b; 3a.

### Exercise B — write a finding
Use: source → observation → limitation → possible follow-up.

## 7. Speaking and writing
**Speaking:** give a 90-second process-review briefing with one finding and one limitation.

**Writing:** prepare a 160–190-word improvement proposal. Include the current situation, evidence, limitation, proposed review and expected information needed to evaluate the proposal.

## 8. Self-check

   A. scope and sources; B. an unsupported conclusion; C. a guessed cause.
2. An observation is:
   A. what the reviewed evidence shows; B. always a recommendation; C. a promise.
3. A baseline is:
   A. a reference point for comparison; B. a final approval; C. a staff list.
4. A proposal should:
   A. identify evidence and limitations; B. guarantee an outcome; C. ignore the source.
5. A small sample:
   A. may not represent the whole process; B. always proves a general trend; C. replaces a full review.

**Key:** 1 A; 2 A; 3 A; 4 A; 5 A.

# Lesson 6. CNC Program Review and Revision Communication

**ID:** `en-c05-s02-l06` · **Level:** B2 · **Suggested duration:** 90 minutes

## Learning outcomes
Students can discuss program-document versions, describe a review finding, distinguish a source-code comment from a validated change, communicate a revision mismatch and write a neutral review note.

## 1. Lead-in
Discuss:
1. Why do digital files need version identifiers?
2. What is the difference between reviewing a file and approving it?
3. Why should a person not guess which version is current?
4. What information should be included in a revision handover?

## 2. Key vocabulary

| Term | Russian | Example |
|---|---|---|
| source file | исходный файл | The source file has a unique ID. |
| revision identifier | обозначение редакции | The revision identifier is shown in the header. |
| version history | история версий | The version history lists changes. |
| change request | запрос на изменение | A change request describes the proposed update. |
| change log | журнал изменений | The change log records the revision. |
| compare | сравнивать | The reviewer compares two file versions. |
| discrepancy | расхождение | A discrepancy was found in the sample package. |
| validation | проверка соответствия правилам | Validation checks defined conditions. |
| approval status | статус утверждения | The approval status is not confirmed. |
| release note | примечание к выпуску | The release note summarizes changes. |
| rollback | возврат к предыдущей версии | A rollback is a controlled version-management action. |
| audit trail | журнал прослеживаемости действий | The audit trail records who changed what and when. |

## 3. Reading: a review is not an approval

Digital engineering files can change over time. A reliable revision process identifies the file, its version, the reason for a change and the person or role responsible for review. A change log should describe what changed without hiding the previous state.

In a classroom CNC example, two sample files may have similar names but different revision identifiers. The reviewer should record the exact names and header information, compare them with the supplied change request and identify any inconsistency. The reviewer should not edit a real machine program or decide which file can be used on equipment.

A review may identify:
- a missing revision label;
- an inconsistent file name and header;
- an incomplete change description;
- a missing link to the change request;
- an unclear approval status.

These are document-control observations. They do not establish whether a program is technically correct, safe or approved for production. Such decisions belong to authorized personnel using the applicable controlled process.

| Field | File A | File B |
|---|---|---|
| Training file ID | CNC-TR-04 | CNC-TR-04 |
| File name | bracket_demo_A | bracket_demo_B |
| Header revision | A | B |
| Change note | initial classroom example | “label updated” |
| Approval status | not stated | not stated |

# Lesson 7. Electrical System Fault-isolation Case Discussion

**ID:** `en-c05-s02-l07` · **Level:** B2 · **Suggested duration:** 90 minutes

## Learning outcomes
Students can describe reported symptoms, distinguish observations from possible causes, discuss evidence and missing information, ask structured questions and write a cautious case summary.

## 1. Lead-in
Discuss:
1. Why is a symptom not the same as a confirmed cause?
2. Which details make a technical report useful to another specialist?
3. Why should a student not turn a classroom scenario into a real troubleshooting instruction?
4. How can a team communicate uncertainty clearly?

## 2. Key vocabulary

| Term | Russian | Example |
|---|---|---|
| symptom | признак / проявление | The reported symptom is intermittent. |
| fault report | сообщение о неисправности | The fault report lists the observed behaviour. |
| fault isolation | локализация неисправности | The term is discussed at a conceptual level. |
| evidence | подтверждающие данные | The evidence is incomplete. |
| possible cause | возможная причина | A possible cause is not a confirmed cause. |
| connector reference | обозначение разъёма | The connector reference appears in the sample diagram. |
| circuit identifier | обозначение цепи | The report includes a circuit identifier. |
| measurement record | запись измерения | The measurement record needs a unit. |
| intermittent | периодический | The symptom is intermittent. |
| reproduce | воспроизвести проявление | The team could not reproduce the symptom in the classroom example. |
| confirm | подтвердить | The available record does not confirm the cause. |
| refer | передать на рассмотрение | The report is referred to the responsible specialist. |

## 3. Reading: evidence before explanation

A fault-isolation discussion begins with a clear description of the reported symptom. The team then identifies what evidence is available, what information is missing and which questions must be referred to the responsible specialist.

A useful case summary separates:
- the equipment or training reference;
- the reported symptom;
- the conditions described in the record;
- available measurements and their units;
- document references and revisions;
- information that is missing;
- the current status;
- the responsible role for follow-up.

A possible cause must not be presented as a confirmed diagnosis. A single observation may have several explanations. A classroom case can teach students how to report information, but it cannot provide instructions for testing, isolating, energizing, de-energizing, repairing or modifying a real aircraft electrical system.

### Fictional case card

**Training reference:** ELEC-CASE-12  
**Reported symptom:** a panel indicator was not visible in one classroom observation and was visible in a later observation.  
**Evidence supplied:** two observation notes; a simplified training diagram; no verified measurement record.  
**Missing information:** test conditions, confirmed diagram applicability and a complete measurement record.  
**Status:** classroom case requires review.  
**Not established:** root cause, component condition or operational status.

## 5. Language focus: possibility, evidence and uncertainty

- “The symptom may be related to…”
- “One possible explanation is…”
- “The available evidence does not confirm…”
- “It is not possible to determine…”

Grammar: modal verbs for cautious interpretation:
- *may* — possibility;
- *might* — weaker possibility;
- *could* — possible explanation;
- *must* — strong deduction only when evidence supports it;
- *cannot* — inability or lack of evidence.

# Lesson 8. Software Test Results and Data-processing Reports

**ID:** `en-c05-s02-l08` · **Level:** B2 · **Suggested duration:** 90 minutes

## Learning outcomes
Students can describe a software test, summarize pass/fail results, identify incomplete or duplicate data, explain a validation rule, distinguish a warning from a confirmed defect and write a concise test summary.

## 1. Lead-in
Discuss:
1. What is the purpose of a software test report?
2. Why should test results include the software version?
3. What can cause duplicate or incomplete records?
4. Why is a warning not always proof of a hardware failure?

## 2. Key vocabulary

| Term | Russian | Example |
|---|---|---|
| test case | тестовый сценарий | Each test case has an ID. |
| test result | результат теста | The result is recorded as pass or fail. |
| expected result | ожидаемый результат | The expected result is defined before the test. |
| actual result | фактический результат | The actual result is compared with the expected result. |
| validation rule | правило проверки данных | The validation rule checks required fields. |
| test environment | тестовая среда | The test environment is identified in the report. |
| software build | сборка программного обеспечения | The report lists the software build. |
| defect | дефект | A defect requires evidence and a reproducible description. |
| warning | предупреждение | A warning is not automatically a confirmed defect. |
| duplicate | дубликат | A duplicate record may affect the summary. |
| missing field | отсутствующее поле | The record contains a missing field. |
| reproducible | воспроизводимый | The issue is reproducible under stated conditions. |
| test coverage | охват тестированием | Test coverage describes which cases were included. |
| log file | файл журнала | The log file contains timestamps. |

## 3. Reading: what a test report should show

A software test report should allow another person to understand what was tested, in which environment and with what result. A useful report identifies the software build, test date, test cases, expected results, actual results and any unresolved issues.

A result marked *fail* means that the actual result did not match the expected result for that test case. It does not automatically explain why the mismatch occurred. The cause may be in the software, the test data, the environment or the test design.

Data validation checks whether information follows defined rules. For example, a classroom test may require a timestamp and a unit field. If either is missing, the record can be flagged for review. A duplicate record may also affect a summary count.

A responsible report distinguishes:
- test result;
- observed behaviour;
- possible explanation;
- confirmed defect;
- unresolved question.

A test report should not claim that an aircraft system is safe, unsafe, operational or unserviceable unless that conclusion is made through the appropriate authorized process and supported by the required evidence. This lesson uses simulated software data only.
